# Symtrail — iOS App (React Native / Expo) Design

**Date:** 2026-06-11
**Status:** Implemented
**Sub-project:** B of 4 (A: backend ✅ implemented, B: iOS app, C: landing page, D: Android app)

## Context

The Rails backend (sub-project A) is implemented and merged: accounts
(email/password + Sign in with Apple), per-account seeded catalogues, and an
offline-first pull/push sync API with per-record last-write-wins. See
`docs/superpowers/specs/2026-06-10-rails-backend-sync-api-design.md`.

A complete React/JSX visual prototype ("Symptio") defines the entire UI:
design tokens (Wiser palette), the Sora typeface, all screens, the symptom and
medication catalogues, and the flare detection/prediction math. The prototype
is the design spec; this sub-project ports it to a production app.

Confirmed decisions:

- **Stack**: React Native via Expo, TypeScript, single codebase for iOS now
  and Android later (sub-project D).
- **Local data**: `expo-sqlite` with a thin hand-written sync client speaking
  the backend's exact pull/push protocol. No WatermelonDB or other ORM.
- **UI state**: SQLite is the single source of truth; screens read it through
  a small reactive query hook. No Redux/Zustand working copy.
- **Dev setup**: Mac + Xcode, no paid Apple Developer account yet. Simulator
  development; email/password auth first; Apple sign-in code ships dormant
  and is enabled when the account is enrolled.
- **Repo layout**: monorepo restructure — Rails moves to `backend/`, the Expo
  app lives in `mobile/` (Expo generates `mobile/ios/` and later
  `mobile/android/`).
- **Visual fidelity**: 1:1 port of the prototype — custom components
  throughout, no native UI kit substitutions.
- **v1 feature scope** (from the project decomposition): core logging
  (symptom/temp/med/note), multi-profile, calendar, flare detection &
  prediction, doctor PDF report, medication reminders, multi-device sync.

## Architecture

**SQLite as the single source of truth.** Every screen reads from the local
database through a `useQuery`-style hook that re-runs when the tables it read
from change (a small in-app event emitter: any write to `entries` notifies
watchers of `entries`). User writes and sync writes flow through the same
door, so the UI cannot disagree with the data. Family-scale volumes make raw
SQLite reads on render-cycle a non-issue.

## Data layer

### Local schema

Mirrors the server exactly: `profiles`, `symptom_types`, `medication_types`,
`entries` with the same columns (string uuid PKs, `client_updated_at`,
`deleted_at`), plus local-only sync bookkeeping per table:

- `dirty` (0/1) — row changed locally since last successful push
- `pending_delete` (0/1) — row deleted locally, tombstone not yet pushed

One `sync_meta` key/value table holds the pull cursor, account id/email, and
settings cache. Server-only columns (`server_version`, `account_id`) are not
stored locally.

Migrations: a simple versioned migration runner (`PRAGMA user_version`).

### Writes

Every local mutation (create/edit from a form): write the row, set
`dirty = 1`, stamp `client_updated_at = now`, emit the table-change event,
schedule a debounced sync. Local deletes set `pending_delete = 1` (row hidden
from queries immediately).

### Reactive reads

`useQuery(tables, sqlFn)` — runs the query, subscribes to the named tables'
change events, re-runs on change. Screens never cache rows in state.

## Sync client

The core is ~200 lines in `sync/client.ts`:

1. **Push**: collect `dirty` rows (grouped per table, parents first) and
   `pending_delete` ids → `POST /api/v1/sync/push`. On `accepted`: clear
   `dirty` / hard-delete the `pending_delete` row. On `rejected: stale`:
   clear `dirty` (the next pull delivers the server's winner). On
   `rejected: invalid`: log to a local debug log, clear `dirty` (no infinite
   retry).
2. **Pull**: `GET /api/v1/sync/pull?since=<cursor>` → upsert `updated` rows,
   **skipping any row that is locally dirty** (unpushed local edits win until
   pushed — the next push/pull cycle resolves via LWW); hard-delete `deleted`
   ids → store the new cursor in `sync_meta`.
3. **Triggers**: app foreground, after any local write (debounced ~3 s), and
   pull-to-refresh on Today/Calendar. Offline or failed requests fail
   silently and retry on the next trigger. Push always runs before pull.
4. **Initial sync**: after sign-in/signup, pull with `since=0` populates the
   seeded catalogues and any existing family data. The app never hardcodes
   catalogue contents.
5. **Auth**: bearer token in SecureStore. 401 on any sync call → clear token,
   route to auth flow (local data preserved). API contract notes: `temp_c`
   arrives as a JSON string ("38.5"); datetimes are ISO 8601 UTC.

## Auth flow

- Email/password sign-up and sign-in against the backend (centered variant
  from the prototype), password reset via the "I have a reset code" flow
  (request → paste code → new password).
- Sign in with Apple: button and `expo-apple-authentication` integration
  implemented but shown only when the entitlement is available (paid account
  enrolled + capability configured). Until then the button is hidden.
- Signed-in users land on Today instantly (local DB), even offline. Sign-out
  calls `DELETE /auth/session`, clears the token, and **keeps local data**
  (signing back into the same account resumes; signing into a different
  account wipes and re-syncs from `since=0`).

## Screens (1:1 from the prototype)

- **Today**: profile switcher, status card, prediction card (when a PFAPA
  profile has ≥2 flares), quick-log buttons, recent entries.
- **Calendar**: month grid with severity heat-mapping, day detail list,
  add-to-day logging.
- **Meds**: medication history grouped by day, upcoming reminders.
- **Profile**: people list (add/edit/delete person), settings (°C/°F synced
  via `PATCH /account`), doctor report, sign-out, account deletion.
- **Log sheets**: symptom (catalogue grid + severity chips), temperature
  (slider with °C/°F + severity bucketing), medication (catalogue + dose +
  optional reminder), each with date/time picker; edit-entry variants.
- **Flare detail**: temperature chart, per-day symptom/med timeline.
- **Entry detail**: view/edit/delete.
- **Auth**: sign-in / sign-up / reset-code screens.
- **Custom symptom/med creation**: add custom catalogue items (label + icon
  pick for symptoms; label/form/strength/dose for meds) — they sync like any
  record.

All styled from `design/tokens.ts` (Wiser palette, severity heat scale, Sora)
with shared components (Card, Sheet, Button, SeverityChip, Avatar, TabBar)
ported from the prototype.

## Domain logic

`domain/flares.ts`: `deriveFlares(entries)` (fever-day clustering, ≤2-day
gaps) and `cycleStats(flares)` (avg/min/max gap, predicted window) ported
verbatim from the prototype's `data.jsx`. Pure functions over typed entry
records. Unit-tested against fixtures derived from the prototype's mock flare
definitions so the port is provably faithful.

`domain/severity.ts`: severity scale and `tempToSeverity` bucketing, ported
as-is.

## Med reminders

Logging/editing a med entry with `reminder_at` schedules/reschedules a local
notification via `expo-notifications`; deleting cancels it. Notification ids
are stored in a local-only table keyed by entry id. Permission is requested
on first reminder use, not at launch. Reminders are device-local in v1
(`reminder_at` syncs as data, but only the device that set it notifies —
documented limitation).

## Doctor report

Build an HTML document (profile header, flare summary with cycle stats,
entries timeline, temperature chart as inline SVG) → `expo-print` →
`expo-sharing` share sheet. Generated entirely on-device from local data.

## Error handling

- Sync failures: silent, retried on next trigger; a subtle "last synced"
  indicator on the Profile screen.
- Form validation mirrors server rules (temp 30–45 °C, required fields) so
  pushes are never rejected as `invalid` in normal use.
- API error envelope (`{error: {code, message}}`) mapped to user-facing
  messages in the auth flows; sync-layer errors never produce dialogs.

## Testing

- **Jest** for `domain/` (flare math vs prototype fixtures), `sync/` (mocked
  fetch + in-memory SQLite: push/pull cycles, dirty-skip rule, stale
  handling, cursor persistence, the two-device convergence scenario run from
  the client side), and `db/` (migrations, query helpers).
- **Component tests** (React Native Testing Library) for the log sheets'
  logic: temp slider ↔ severity bucketing, severity chip selection,
  reminder toggle behavior.
- **Manual Simulator passes** for visual fidelity against the prototype
  screenshots.
